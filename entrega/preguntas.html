Pregunta 1 · Para qué sirve y cómo se configura el NAT

En la red del proyecto, ¿cuál es la función del NAT Gateway y cómo se configura?

  1. A.Publica la aplicación en Internet: recibe las peticiones de los usuarios y las reparte entre los servidores. Se configura en la subred de datos con un puerto de escucha.
  2. B.Permite que los servidores de la subred privada inicien conexiones hacia Internet usando una única dirección pública, sin que desde Internet se pueda iniciar una conexión hacia ellos. Se crea en una subred pública con una IP elástica, y en la tabla de ruteo de la subred privada se agrega la ruta 0.0.0.0/0 hacia el NAT.
  3. C.Traduce nombres de dominio a direcciones IP dentro de la VPC. Se configura asociando una zona DNS a cada subred.
  4. D.Cifra el tráfico entre la subred pública y la privada. Se crea en la subred privada y se agrega la ruta 0.0.0.0/0 en la tabla de ruteo de la subred pública.
Respuesta correcta: B

Explicación

NAT significa Network Address Translation (traducción de direcciones de red). Los servidores de la capa de aplicación solo tienen direcciones privadas (10.0.11.x), que no existen en Internet. Aun así necesitan salir: para instalar Docker, descargar la imagen base y recibir actualizaciones. El NAT Gateway recibe ese tráfico, cambia la dirección de origen privada por su propia dirección pública y lo envía a Internet; cuando llega la respuesta, la devuelve al servidor que la pidió. Como solo guarda las conexiones que se iniciaron desde dentro, nadie puede abrir una conexión hacia los servidores desde fuera.

El «enlace público». El NAT necesita él mismo salida a Internet, por eso se ubica en una subred pública: una subred cuya tabla de ruteo apunta a la puerta de enlace de Internet. La cadena completa es: servidor privado → NAT (subred pública) → puerta de enlace de Internet → Internet.

Configuración, en tres piezas (archivo infra/red.tf):

# 1. Una dirección pública fija (IP elástica) para el NAT
resource "aws_eip" "nat" {
  domain = "vpc"
}

# 2. El NAT, ubicado en una subred PÚBLICA y con esa dirección
resource "aws_nat_gateway" "nat" {
  allocation_id = aws_eip.nat.id
  subnet_id     = aws_subnet.publica[0].id
  depends_on    = [aws_internet_gateway.igw]
}

# 3. La tabla de ruteo de la capa de aplicación envía "todo lo demás" al NAT
resource "aws_route_table" "app" {
  vpc_id = aws_vpc.principal.id
  route {
    cidr_block     = "0.0.0.0/0"
    nat_gateway_id = aws_nat_gateway.nat.id
  }
}

Comprobación en el proyecto. Desde el servidor de la aplicación se consultó cuál era su dirección vista desde Internet y la respuesta fue 77.114.18.158, la IP elástica del NAT y no la del servidor (prueba 7). En sentido contrario, los intentos de conexión desde Internet hacia el servidor no obtuvieron respuesta (prueba 3).

Por qué las otras no: A describe al balanceador de carga, que es quien recibe a los usuarios. C describe al servicio DNS. D invierte la configuración (el NAT va en la subred pública y la ruta en la tabla de la privada) y el NAT no cifra.

La capa de datos no usa el NAT: su tabla de ruteo no tiene ninguna ruta hacia fuera. Y si la red usara IPv6, el NAT no haría falta para ese tráfico: todas las direcciones IPv6 son públicas y la salida «solo de ida» se logra con una puerta de enlace solo de salida (egress-only internet gateway).

Pregunta 2 · Cómo se define la seguridad entre capas

¿Cómo se define en el proyecto la seguridad entre la capa pública, la de aplicación y la de datos?

  1. A.Asignando a cada subred un identificador de VLAN 802.1Q distinto, de modo que las tramas de una capa no lleguen a las otras.
  2. B.Ubicando cada capa en una zona de disponibilidad diferente: los recursos de zonas distintas no pueden comunicarse entre sí.
  3. C.Con tres mecanismos declarados en Terraform: una tabla de ruteo por capa, Security Groups encadenados en los que cada capa solo acepta al grupo de la capa anterior en un puerto concreto, y una NACL en la subred de datos que solo admite a las subredes de aplicación.
  4. D.Instalando un firewall de software en cada servidor y abriendo manualmente los puertos necesarios desde la consola de AWS.
Respuesta correcta: C

Explicación

La seguridad se define con tres barreras independientes, todas escritas como código en infra/red.tf e infra/seguridad.tf. Si una quedara mal configurada, las otras dos siguen protegiendo.

BarreraQué controlaCómo quedó
Tablas de ruteoPor dónde puede salir cada subredPública: 0.0.0.0/0 → Internet. Aplicación: 0.0.0.0/0 → NAT. Datos: solo la ruta local.
Security Groups
(con estado, por servidor)		Quién puede hablarle a cada equipoBalanceador: puerto 80 desde Internet. Aplicación: 8080 solo desde el grupo del balanceador. Datos: 3306 solo desde el grupo de la aplicación.
NACL
(sin estado, por subred)		Qué entra y sale de la subred de datosEntrada: 3306 desde 10.0.11.0/24 y 10.0.12.0/24. Salida: puertos 1024–65535 hacia esas subredes. Todo lo demás se deniega.

La pieza clave es el encadenamiento: la regla no nombra una dirección IP sino a otro Security Group. Así, la base de datos acepta a «quien pertenezca al grupo de la aplicación», sin importar cuántos servidores haya ni qué IP tengan:

# infra/seguridad.tf — MySQL solo desde el grupo de la aplicación
resource "aws_vpc_security_group_ingress_rule" "datos_desde_app" {
  security_group_id            = aws_security_group.datos.id
  referenced_security_group_id = aws_security_group.app.id
  ip_protocol                  = "tcp"
  from_port                    = 3306
  to_port                      = 3306
}

# infra/red.tf — la tabla de ruteo de datos no tiene ninguna ruta hacia fuera
resource "aws_route_table" "datos" {
  vpc_id = aws_vpc.principal.id
}

Comprobación en el proyecto. Un equipo ubicado en la subred pública, dentro de la misma VPC, intentó abrir el puerto 3306 de la base de datos y el 8080 de la aplicación: ninguno respondió (pruebas 4 y 5). El servidor de la aplicación sí abrió el 3306 (prueba 6). Los registros de tráfico de la VPC muestran ACCEPT para la aplicación y REJECT para el equipo de la subred pública.

Por qué las otras no: A no aplica porque en AWS el cliente no configura VLANs dentro de la VPC (la única etiqueta 802.1Q aparece en Direct Connect). B es falsa: las subredes de zonas distintas de una misma VPC sí se comunican por la ruta local; las zonas dan disponibilidad, no aislamiento. D no es lo que se hizo: nada se abrió a mano y ningún servidor depende de un firewall propio; las reglas están en la red y en el código.

Pregunta 3 · Qué es Terraform

¿Qué es Terraform y qué papel cumplió en el proyecto?

  1. A.Una herramienta de infraestructura como código: la red, los servidores y la base de datos se describen en archivos de texto, y Terraform se encarga de crearlos, modificarlos o borrarlos en AWS.
  2. B.Un servicio de AWS que supervisa el tráfico de la red y registra qué conexiones se aceptan o se rechazan.
  3. C.Un motor de contenedores que empaqueta la aplicación con sus dependencias para ejecutarla en el servidor.
  4. D.El lenguaje de programación en el que está escrita la aplicación de reservas.
Respuesta correcta: A

Explicación

Terraform es una herramienta de la empresa HashiCorp para manejar infraestructura como código. En lugar de crear cada recurso con clics en la consola, se escribe en archivos .tf el resultado que se quiere («una VPC con este rango», «dos subredes de datos», «esta regla») y Terraform calcula qué debe crear y en qué orden. Es declarativo: se describe el destino, no los pasos.

Se usa con tres comandos:

ComandoQué haceEn el proyecto
terraform initDescarga el conector («proveedor») que sabe hablar con AWSProveedor hashicorp/aws 6.73
terraform planCompara el código con lo que existe y muestra los cambios, sin ejecutarlos«Plan: 46 to add»
terraform applyEjecuta el plan46 recursos en unos 7 minutos

Terraform guarda un archivo de estado con lo que ya creó. Por eso, repetir apply sin cambiar el código responde «No changes», y terraform destroy puede borrar exactamente lo que creó.

Papel en el proyecto. Toda la segmentación está en cuatro archivos: red.tf (VPC, subredes, rutas, NAT y NACL), seguridad.tf (Security Groups), datos.tf (MySQL) y computo.tf (servidores y balanceador). Esto hace que la red sea reproducible: cualquier persona con el repositorio la crea con un comando, como muestra el manual.

Por qué las otras no: B describe los registros de tráfico de la VPC (flow logs) con CloudWatch. C describe a Docker, que también se usó, pero para la aplicación. D es Node.js (JavaScript); Terraform usa su propio lenguaje de configuración, HCL, y no sirve para programar aplicaciones.
